# 路线探索与交接

首次接入、混合操作或计划替换执行路径时按需阅读。低风险小修复沿用已验证路径即可。

## 路线切换原则

- 已验证路线能够满足业务正确性、运行规模和维护要求时，默认继续复用。
- 仅在出现可测量的性能瓶颈、已观察到的可靠性问题、维护成本过高、业务能力缺失，或发现明显更合适的正式接口时，才评估替换。UI → API 和 API → UI 都按同一标准判断。
- 切换前验证新旧路线在业务对象及租户、字段语义、权限、副作用、完成判据和错误恢复上等价。若存在业务差异，明确其影响；不能把它当作等价替换。
- 写入结果不明时，先核对远端业务状态；不得自动切换执行器再次提交。

## 探索与交接

- **先拆业务，再选工具。** 针对会影响实现的步骤，明确业务对象、前置状态、读写性质、完成信号；提交受理和最终生效可能是两步。对正式 API 核对权限范围、业务字段及状态、分页、限流和批量能力；对 DOM/视觉核对目标定位、页面状态与结果回读。
- **区分三类接口证据。** 官方文档说明受支持的契约；在获准页面操作中观察响应，只证明该样本的页面行为；主动调用未公开接口须另有明确许可，并核对业务语义、维护成本和运行条件。不要绕过访问控制、验证码或站点限制，也不要留存会话凭据。不能证明可用时保留为候选或采用已证实的页面路径。
- **验证决定路线的最小样本。** 比较同一记录、过滤条件、字段口径和远端状态，不靠 HTTP 200、toast 或页面截图判定业务成功。写入验证只限获准环境和范围；未测的写入可以交接为待验证。规模或性能影响选型时，先量现有路径的瓶颈，再比较替代路线。
- **混合路线共享业务规则。** 只有确有收益时才混用执行方式。不同路线使用相同业务对象标识、完成判据与写入恢复规则。常规步骤用确定性实现，视觉或 Agent 可用于探索及定位异常；异常不自动升级权限或触发另一执行器补写。

交接用几行或一张表即可：**操作｜拟选路线及理由｜证据状态与来源｜完成判据｜缺口及影响**。区分已观察（看到行为）、已推断（尚无实证）、已验证（注明样本和适用范围）、未验证（未实际测到）、已阻塞（有明确障碍）。已观察的网络响应可以和未验证的主动接口路线同时存在。关键步骤已有足够实现证据，或缺口和下一步已明确，就停止探索。

## 沉淀可复用能力

- **站点级契约**：入口、认证方式、公共页面结构与接口约束，供不同任务按需读取。
- **任务级契约**：具体流程、步骤路线、业务成功信号与验证样本。
- **已验证能力**：有多处实际复用需求时，从契约中封装独立操作，例如列表查询、详情读取、增量分页、填表或结果回读。写明输入、输出、前置状态、权限及副作用、完成信号、可辨别的失败状态和验证范围。查询与提交若有不同权限或副作用，应分别表达。

优先使用已有页面适配器、API 客户端、HTTP 采集器或混合模块。在验证仍适用的站点、角色和契约范围内复用；页面、权限、字段或接口变化时只重验受影响操作。仅在重复出现同类适配工作且能验证生成结果时才考虑生成机制。无需为每项能力创建新 Skill、注册中心或独立文档。
